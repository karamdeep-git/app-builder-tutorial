# Configuration Reference — Keys, Secrets & URLs

Every credential and URL this project uses, where to get it, where it's set, and how
it flows from `.env` into the running code. All real secret *values* below are
replaced with placeholders — only the key *names* and file *paths* are real.

There are two separate credential "worlds" in this project:

1. **Adobe Developer Console / Adobe I/O Runtime** — mostly auto-generated by the
   `aio` CLI, rarely hand-typed.
2. **Adobe Commerce (Magento)** — manually created in the Magento Admin UI, hand-
   entered into `.env`.

Everything lives in one file: **`/Users/kinex/Sites/app-builder-tutorial/.env`**
(gitignored — never commit this file).

---

## 1. Adobe Developer Console / I/O Runtime credentials

**Where they come from:** you don't hand-type these. Run `aio app use` from the
project root, pick your Org → Project → Workspace in the interactive prompt, and the
CLI downloads the workspace config and writes both `.env` and `.aio` for you.

```bash
# Run this from /Users/kinex/Sites/app-builder-tutorial
aio app use
# -> prompts: select Org "Kinex Media Partner Sandbox", Project "TestKnm", Workspace "Stage"
# -> writes/overwrites .env and .aio automatically
```

**`.env`** (`/Users/kinex/Sites/app-builder-tutorial/.env`):

```bash
# Runtime (OpenWhisk) auth — "<namespace>:<key>" pair. This is what lets `aio app
# deploy` push actions to YOUR namespace, and what the deployed action URLs are
# scoped under. Get it again any time via: aio app use (or aio console ws list)
AIO_runtime_auth=4033606-testknm-stage:AbCdEf123...                # <namespace>:<key>

# The Adobe I/O Runtime namespace actions get deployed into. Shows up directly in
# every deployed action's URL, e.g.:
#   https://4033606-testknm-stage.adobeioruntime.net/api/v1/web/product/list
AIO_runtime_namespace=4033606-testknm-stage

# Fixed Adobe endpoint — the API host Runtime commands talk to. Never changes
# per-project; same for every App Builder app.
AIO_runtime_apihost=https://adobeioruntime.net

# --- Server-to-Server OAuth credentials for this specific Workspace ("Stage") ---
# Get these from: Adobe Developer Console (https://developer.adobe.com/console)
#   -> your Org -> Project "TestKnm" -> Workspace "Stage"
#   -> the "OAuth Server-to-Server" credential tile -> "View" / "Retrieve Client Secret"
# These are what this app would use to call Adobe's OWN APIs (I/O Events, I/O
# Management API) as itself, not as a logged-in user. The long env var name is
# literally "Credential_in_<Project>_-_<Workspace>", auto-generated by `aio app use`.
AIO_ims_contexts_Credential__in__TestKnm__-__Stage_client__id=<your-client-id>
AIO_ims_contexts_Credential__in__TestKnm__-__Stage_client__secrets=["<your-client-secret>"]
AIO_ims_contexts_Credential__in__TestKnm__-__Stage_technical__account__email=<tech-account>@techacct.adobe.com
AIO_ims_contexts_Credential__in__TestKnm__-__Stage_technical__account__id=<tech-account-id>@techacct.adobe.com
AIO_ims_contexts_Credential__in__TestKnm__-__Stage_scopes=["AdobeID","openid","read_organizations", ...]
AIO_ims_contexts_Credential__in__TestKnm__-__Stage_ims__org__id=<your-org-id>@AdobeOrg

# Same OAuth Server-to-Server credential, duplicated under the "generic" names some
# SDKs/libraries expect instead of the long Credential_in_... form above. Same
# source (Developer Console -> Workspace -> OAuth Server-to-Server tile).
SERVICE_API_KEY=<your-client-id>                                  # = the client_id above
IMS_OAUTH_S2S_CLIENT_ID=<your-client-id>
IMS_OAUTH_S2S_CLIENT_SECRET=<your-client-secret>
IMS_OAUTH_S2S_ORG_ID=<your-org-id>@AdobeOrg
IMS_OAUTH_S2S_SCOPES=["AdobeID","openid","read_organizations", ...]
```

**Where this is *used*:** none of these are referenced directly by our own action
code (no `params.AIO_runtime_auth` anywhere in `actions-src/`). The `aio` CLI itself
reads them straight out of `.env` whenever you run `aio app build` / `aio app
deploy` / `aio app use`. You only ever touch this block again if you switch Adobe
Developer Console projects or workspaces — just re-run `aio app use`.

**`.aio`** (`/Users/kinex/Sites/app-builder-tutorial/.aio`) — a companion,
non-secret file also written by `aio app use`. Holds the human-readable project/org/
workspace names and the deployed URLs (no keys):

```jsonc
// .aio (excerpt) — informational only, never hand-edited
{
  "project": {
    "name": "TestKnm",
    "org": { "id": "4033606", "name": "Kinex Media Partner Sandbox" },
    "workspace": {
      "name": "Stage",
      // These two URLs are where your deployed actions/app end up living:
      "action_url": "https://4033606-testknm-stage.adobeioruntime.net",
      "app_url": "https://4033606-testknm-stage.adobeio-static.net"
    }
  }
}
```

## 2. Adobe Commerce (Magento) credentials

These you create yourself in Magento Admin, then hand-type into `.env`. This is the
block that actually matters for day-to-day development on this app.

### 2a. `COMMERCE_BASE_URL` — where Magento lives

```bash
# .env
# The externally-reachable URL of your Magento instance. Our Adobe I/O Runtime
# actions run in Adobe's cloud, NOT on your Mac, so "localhost" would not work here
# - that's why this points at an ngrok tunnel into the local Magento vhost instead
# of e.g. http://testapp.local/. MUST end with a trailing slash.
COMMERCE_BASE_URL=https://<your-random-subdomain>.ngrok-free.dev/
```

**Where you get it:** start the tunnel, then copy the `https://...ngrok-free.dev`
URL it prints:

```bash
ngrok http 80
# Forwarding   https://<your-random-subdomain>.ngrok-free.dev -> http://localhost:80
#                      ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^ copy this into COMMERCE_BASE_URL
```

**Gotcha:** every time you restart `ngrok` (free plan, no reserved domain) you get a
*new* random subdomain, and you have to update `COMMERCE_BASE_URL` in `.env` *and*
redeploy (`aio app deploy`) for the actions to pick it up. The Apache vhost for the
real Magento codebase also needs that ngrok hostname in its `ServerAlias` — see
`/opt/homebrew/etc/httpd/extra/httpd-vhosts.conf` (vhost for `testapp`, the actual
Magento instance this app talks to — confirmed via Apache access logs, *not*
`m248p5`, which is a different, unrelated local Magento install on the same
machine).

### 2b. OAuth 1.0a keys — used for every normal product/indexer/command API call

```bash
# .env
COMMERCE_CONSUMER_KEY=<your-consumer-key>
COMMERCE_CONSUMER_SECRET=<your-consumer-secret>
COMMERCE_ACCESS_TOKEN=<your-access-token>
COMMERCE_ACCESS_TOKEN_SECRET=<your-access-token-secret>
COMMERCE_STORE_CODES=[]                 # leave as [] unless you need multi-store routing
```

**Where you get them** — Magento Admin:

```text
Magento Admin -> System -> Extensions -> Integrations
  -> "Add New Integration"
  -> name it (e.g. "AppBuilderIntegration"), fill in the current admin password
  -> Save -> click "Activate" -> approve the permissions Magento shows you
  -> Magento then displays, ONE TIME ONLY:
       Consumer Key          -> COMMERCE_CONSUMER_KEY
       Consumer Secret       -> COMMERCE_CONSUMER_SECRET
       Access Token          -> COMMERCE_ACCESS_TOKEN
       Access Token Secret   -> COMMERCE_ACCESS_TOKEN_SECRET
```

If you lose them, there's no "reveal" button — deactivate and reactivate the same
Integration to generate a fresh set.

**How this flows into actual code** — three steps, always the same pattern:

```yaml
# Step 1: actions-src/product/actions.config.yaml (one block per action that needs
# Commerce access) — the $VAR syntax means "read this from .env at deploy time"
update:
  function: ../../actions/product/update/index.js
  web: "yes"
  runtime: nodejs:20
  inputs:
    LOG_LEVEL: debug
    COMMERCE_BASE_URL: $COMMERCE_BASE_URL                       # <- from .env
    COMMERCE_STORE_CODES: $COMMERCE_STORE_CODES                 # <- from .env
    COMMERCE_CONSUMER_KEY: $COMMERCE_CONSUMER_KEY                # <- from .env
    COMMERCE_CONSUMER_SECRET: $COMMERCE_CONSUMER_SECRET          # <- from .env
    COMMERCE_ACCESS_TOKEN: $COMMERCE_ACCESS_TOKEN                # <- from .env
    COMMERCE_ACCESS_TOKEN_SECRET: $COMMERCE_ACCESS_TOKEN_SECRET  # <- from .env
```

```yaml
# Step 2: app.config.yaml — wires that file into the deployed action manifest.
# Nothing to edit here when adding new Commerce credentials, just when adding a
# whole new action *package* (see the existing product/indexer/commands examples).
application:
  runtimeManifest:
    packages:
      product:
        actions:
          $include: ./actions-src/product/actions.config.yaml
```

```typescript
// Step 3: actions-src/product/update/index.ts — the action receives everything
// from `inputs` above as plain fields on its `params` object at runtime.
export async function main(params: ProductUpdateParams): Promise<AppResponse> {
  // params.COMMERCE_BASE_URL        === the ngrok URL from .env
  // params.COMMERCE_CONSUMER_KEY    === the Integration's Consumer Key from .env
  // ...etc - AdobeCommerceClient.create() below reads all four OAuth1 fields off
  // `params` and signs every outgoing request with them.
  const client = AdobeCommerceClient.create(params, {
    storeCode: "default",
    storeUrl: params.COMMERCE_BASE_URL,
  });
}
```

Defined in: `actions-src/utils/adobe-commerce/types/request.ts`

```typescript
// The TypeScript shape that documents exactly which four Commerce keys any
// action can expect on `params`, once its actions.config.yaml binds them.
export interface CommerceParams {
  COMMERCE_BASE_URL: string;
  COMMERCE_CONSUMER_KEY: string;
  COMMERCE_CONSUMER_SECRET: string;
  COMMERCE_ACCESS_TOKEN: string;
  COMMERCE_ACCESS_TOKEN_SECRET: string;
  COMMERCE_STORE_CODES: string;
}
```

### 2c. `COMMERCE_ADMIN_USERNAME` / `COMMERCE_ADMIN_PASSWORD` — real admin login, not an API key

```bash
# .env
# A REAL Magento Admin user's login (not an Integration, not OAuth). Used ONLY by
# actions-src/utils/adobe-commerce/admin-session-client.ts, to log into Magento
# Admin the same way a human would (cookie session + CSRF form_key), because the
# "sync product status to All Store Views" feature has to drive an internal Admin
# controller that has no OAuth-reachable equivalent.
COMMERCE_ADMIN_USERNAME=<an-existing-admin-username>
COMMERCE_ADMIN_PASSWORD=<that-admin-s-password>
```

**Where you get it:** it's just an existing Magento Admin account —
`Magento Admin -> System -> Permissions -> All Users` (or whichever admin user you
already log into the Admin panel with). No generation step, unlike the OAuth keys.

**Security note:** this is a materially more sensitive credential than the OAuth1
keys above (a real admin login vs. a scoped API integration) — treat `.env` as
extra-sensitive while this is set, and rotate the password if `.env` is ever
exposed.

**How it flows into code** — same three-step pattern as §2b, but only bound on the
one action that needs it:

```yaml
# actions-src/product/actions.config.yaml
update:
  inputs:
    COMMERCE_ADMIN_USERNAME: $COMMERCE_ADMIN_USERNAME   # only `product/update` needs this
    COMMERCE_ADMIN_PASSWORD: $COMMERCE_ADMIN_PASSWORD
```

```typescript
// actions-src/product/update/index.ts
// params.COMMERCE_ADMIN_USERNAME / params.COMMERCE_ADMIN_PASSWORD are optional -
// if unset, the All-Store-Views sync step is silently skipped (see
// syncStatusToAllStoreViews()) and only the normal OAuth1 write happens.
if (!params.COMMERCE_ADMIN_USERNAME || !params.COMMERCE_ADMIN_PASSWORD) {
  return; // best-effort feature, not a hard requirement
}
```

## 3. Action URLs (`web-src/src/config.json`) — generated, never hand-edited

```jsonc
// web-src/src/config.json (excerpt) — DO NOT edit this file by hand. It's
// regenerated every time you run `aio app build` or `aio app deploy`, by
// combining AIO_runtime_namespace (.env) with every action name declared across
// all the actions.config.yaml files included from app.config.yaml.
{
  "product/update": "https://4033606-testknm-stage.adobeio-static.net/api/v1/web/product/update",
  "indexer/reindex": "https://4033606-testknm-stage.adobeio-static.net/api/v1/web/indexer/reindex",
  "commands/run": "https://4033606-testknm-stage.adobeio-static.net/api/v1/web/commands/run"
}
```

**How the frontend uses it:**

```javascript
// web-src/src/components/ProductList.js
import allActions from "../config.json";
import actionWebInvoke from "../utils";

// allActions["product/update"] is one of the generated URLs above - this is the
// ONLY place the frontend ever learns a backend action's URL.
await actionWebInvoke(allActions["product/update"], authHeaders, { data: product }, { method: "POST" });
```

If an action you expect is missing from `config.json`, it means the action's
`actions.config.yaml` entry hasn't been deployed yet — run `aio app deploy`.

## 4. Magento-side URLs used by the two custom PHP modules

These aren't `.env` values at all — they're Magento REST routes defined *by us*, in
the two custom modules living directly in the Magento codebase (not this repo):

| Route | Defined in |
|---|---|
| `/V1/kinex-reindex/*` | `/Users/kinex/Sites/testapp/app/code/Kinex/Reindex/etc/webapi.xml` |
| `/V1/kinex-commands/*` | `/Users/kinex/Sites/testapp/app/code/Kinex/CommandManager/etc/webapi.xml` |

They're reached the exact same way as any other Commerce call — through
`COMMERCE_BASE_URL` + the OAuth1 keys from §2b — because the Adobe Commerce
Integration created in §2b already has full (`Magento_Backend::all`) Admin access,
so no extra Magento-side permission grant was needed for these custom routes.

## 5. Quick checklist — setting this up on a new machine

1. `aio app use` → picks the Adobe org/project/workspace, writes §1's block into
   `.env` automatically.
2. Start your local Magento, then `ngrok http 80` → copy the printed URL into
   `COMMERCE_BASE_URL` (§2a).
3. Magento Admin → System → Integrations → create + activate one → copy its four
   keys into §2b.
4. Pick an existing Magento Admin login → put it into `COMMERCE_ADMIN_USERNAME` /
   `COMMERCE_ADMIN_PASSWORD` (§2c) — skip this if you don't need product-status
   All-Store-Views sync.
5. `aio app deploy` → regenerates `web-src/src/config.json` (§3) and pushes
   everything live.
